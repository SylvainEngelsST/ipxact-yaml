# Relationship to IEEE 1685-2022

IEEE 1685-2022 (IP-XACT) is the conceptual reference for identity, memory maps,
registers, fields, software access, and reset descriptions. This project is a
**constrained YAML authoring profile**, not the official IEEE schema, not an
IEEE publication, and not a complete YAML transcription of the standard.

This document explains the project's mapping in original prose. For normative
requirements, consult an authorized copy of IEEE 1685-2022. No clause-level
conformance or lossless XML round-trip is claimed.

## Conceptual correspondence

| ipxYAML concept | Relationship / profile decision |
|---|---|
| `vlnv` | Vendor/library/name/version identity, separate from instance identity. |
| IP `maps[]` | Local addressable regions. This profile combines memory-map selection with a region's extent, data width, and usage; it does not expose the full XML memory-map/address-block hierarchy. |
| `usage` | Distinguishes register storage, memory, and reserved regions. |
| Register `offset`, `width_bits` | Byte-relative placement and bit size. |
| Field `lsb`, `width_bits` | Contiguous bit slice within a register. |
| `access` | Software-facing access vocabulary; not hardware permission. |
| `modified_write_value`, `read_action` | Constrained software side-effect vocabulary. |
| `reset_types`, field `resets` | Named reset types with field-relative values and masks. |
| System `address_spaces`, instances, mappings | Project hierarchy/placement abstraction for reusable YAML definitions, not a complete IP-XACT interconnect or design model. |

## Explicit project conventions

- `schema_version`, `naming_profile`, `kind`, uppercase/lowercase naming rules,
  and relative YAML `source` references are project authoring conventions.
- Byte addressing is fixed. There is no configurable address-unit size.
- `hwAccess` separately records hardware-side permissions. Treat this
  spelling, vocabulary, and its validation rule as part of this profile's
  hardware-access convention, not a claim about a same-named IEEE element.
- Hardware-write permission requires `volatile: true`. Volatility and hardware
  permissions remain separately authored; neither is inferred from software access.
- The accepted software effects are intentionally limited to those listed in the
  [field reference](reference.md). Arbitrary user-defined effects are unsupported.
- Reset priority, hardware-versus-software priority, and illegal-access responses
  are prose requirements, not machine-readable arbitration rules.
- All register/field permissions are explicit at the field level. No inherited
  register permission or automatic reset value is provided.
- Registers are limited to 8, 16, 32, or 64 bits. Reset values/masks are quoted
  hexadecimal strings bounded by the field width, with a 64-bit maximum. These
  are project profile decisions, not claims of equivalent IEEE restrictions.

## Deliberate scope limits

This contract does not model bus interfaces, ports, signals, wire connectivity,
views, file sets, parameters/expressions, configurable elements, register arrays,
register files, alternate registers, enumerated field values, endianness,
interrupt connectivity, or the full IEEE component/design ecosystem.
Unknown properties are rejected rather than preserved as vendor extensions.

An XML exporter may translate this profile to a supported subset of IP-XACT.
That exporter's capabilities and conformance must be assessed separately;
schema-valid YAML alone is not proof of conforming IEEE XML or correct RTL.
